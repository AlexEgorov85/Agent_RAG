## 1. Цель

Перевести пользовательский интерфейс Agent_RAG со Streamlit на современный WebUI,
предназначенный для работы с аналитическими исследованиями, корпоративными документами
и результатами Agentic RAG.

Новый интерфейс должен обеспечивать:

- полноценный диалог с исследовательским агентом;
- отображение хода выполнения исследования;
- просмотр найденных документов и доказательств;
- интерактивную работу с цитатами и первоисточниками;
- отображение таблиц, графиков и сравнений;
- анализ изменений структуры и содержания годовых отчётов;
- управление историей исследований;
- сохранение контекста текущего исследования между сообщениями.

**Главное требование:** модернизация интерфейса не должна приводить к переписыванию
RAG-ядра или переносу бизнес-логики в frontend.

Существующие механизмы ingestion, retrieval, reranking, graph retrieval, agent
orchestration и answer generation остаются в Python.

### 1.1. Что не считается результатом

- Визуальный прототип без подключения к `AgentService`.
- Второй, независимый чат-бэкенд «для фронтенда».
- UI, который сам считает CAGR, проценты, разницу или «достаточность» доказательств.
- UI, который показывает этапы исследования, не полученные от backend.
- UI, который хранит историю только в браузере.

### 1.2. Критерий успеха

Пользователь открывает React-приложение, создаёт исследование, задаёт вопрос,
видит реальный прогресс выполнения, получает ответ с проверяемыми источниками,
открывает первоисточник, задаёт уточняющий вопрос, перезагружает страницу и
продолжает работу. Все содержательные данные при этом получены от Python-ядра.

## 2. Основные архитектурные решения

### 2.1. Технологический стек

| Слой | Технология | Роль | Ограничение |
|---|---|---|---|
| UI runtime | React + TypeScript + Vite | SPA, сборка, dev-сервер | Node LTS ≥ 20, lockfile в репозитории |
| Чат | assistant-ui | примитивы Thread / Composer / Message | можно использовать без его runtime |
| Стили | Tailwind CSS | дизайн-токены и компоновка | без CSS-in-JS библиотек |
| Компоненты | shadcn/ui | кнопки, диалоги, popover, tabs | исходники компонентов принадлежат проекту |
| Графики | Recharts | линии, столбцы, группировка | данные приходят готовыми с backend |
| Таблицы | TanStack Table | сортировка, ширины, закрепление | без аналитических вычислений |
| Серверные данные | TanStack Query | кэш, инвалидация, retry | не хранить в нём streaming-буфер |
| Backend adapter | FastAPI + SSE | HTTP-контракт и поток событий | тонкий слой над `AgentService` |
| Хранилище истории | SQLite (stdlib `sqlite3`) | исследования и сообщения | без внешней БД и очередей |
| Модульные тесты UI | Vitest + Testing Library | компоненты и reducers | без сети и LLM |
| E2E | Playwright | пользовательские сценарии | против fixture-backend и реального API |

Конкретные версии библиотек фиксируются в `package-lock.json` / lock-файле
выбранного пакетного менеджера. В спецификации версии не задаются.

Adapter не является отдельным «движком»: он вызывает существующий
`AgentService` (`src/agent/service.py`), сериализует его события и хранит
пользовательскую историю. Никакой второй оркестрации нет.

### 2.3. Границы ответственности

| Frontend | Adapter | Python-ядро |
|---|---|---|
| отображение интерфейса | приём и валидация HTTP-запроса | планирование действий агента |
| ввод и отправка запросов | проверка владельца исследования | retrieval и reranking |
| отображение сообщений и событий | сериализация событий | Graph RAG и structure tools |
| состояние UI и навигация | хранение истории исследований | сбор контекста |
| визуализация таблиц и графиков | отмена и жизненный цикл запроса | анализ документов |
| форматирование чисел и единиц | единый формат ошибок | генерация ответа |
| сортировка/фильтрация отображения | ограничения размера payload | проверка цитат |
| экспорт уже полученных данных в CSV | доступ к chunk-метаданным | расчёты (`calculations.py`) |

Frontend может:

- форматировать числа для отображения (`Intl.NumberFormat`);
- группировать строки таблицы по уже переданным `metric` + `unit`;
- сортировать, сворачивать и фильтровать отображаемые строки;
- сериализовать отображаемую таблицу в CSV без изменения значений.

Frontend не может:

- вычислять проценты, CAGR, разницу, суммы, доли и «средние»;
- объединять значения с разными единицами;
- определять, достаточно ли доказательств;
- решать, есть ли показатель в отчёте, если backend этого не сообщил;
- интерпретировать внутреннее состояние `AgentService` по косвенным признакам.

### 2.4. Фактическое состояние на дату аудита

Сверено с кодом рабочего дерева.

| Слой | Что есть сейчас | Следствие для проекта |
|---|---|---|
| UI | `src/ui/app.py` — Streamlit-чат; `src/ui/citations.py` — карточки цитат | переиспользуются только идеи и контракты, не код |
| Вызов агента | UI вызывает `AgentService.stream()` / `ask()` в процессе | HTTP-слой отсутствует и должен быть создан |
| HTTP-сервер | в `requirements.txt` нет FastAPI/uvicorn/Flask; ASGI-приложения нет | §7 и §10 — новая работа, а не обёртка |
| Поток событий | `AgentService.stream()` — итератор, наполняемый фоновым потоком через `Queue` | adapter должен корректно передавать его в SSE, не блокируя event loop |
| События | `run_started`, `analysis_completed`, `tool_started`, `tool_completed`, `answer_started`, `run_completed`, `run_failed` | `answer_delta` и `evidence_updated` сейчас **не** публикуются |
| Идентификаторы | `request_id` (UUID на запуск), `conversation_id` (UUID на сессию) | `user_id`, владельца и авторизации нет |
| История | `AgentService._conversation_history` в памяти процесса, 10 ходов, обрезка 4000 символов, редактирование секретов; видимые сообщения — в `st.session_state` | после перезапуска процесса контекст теряется; персистентности нет |
| Answer / Citation | `status`, `answer`, `citations`, `facts`, `warnings`, `calculations`; цитата: `chunk_id`, `doc_id`, `year`, `issuer`, `page_pdf`, `page_label`, `section_path`, `quote` | нет `document_title`, `source_type`, `page_end`, полного текста chunk |
| Chunk-артефакты | `data/dev/chunks/*.json`: `title` (название отчёта), `kind` (`text`/`table`), `breadcrumbs`, `section_path`, `page_pdf`, `page_label`, `evidence_id` (уровня страницы) | полный текст и тип источника можно отдать отдельным endpoint |
| Facts / calculations | `Answer.facts` — `list[dict]` без жёсткой схемы; `src/engine/calculations.py` реализован, но в генерации не подключён | аналитические представления зависят от этапа P6 в `spec_agent_enhancement.md` |
| Coverage | `expected_years` / `covered_years` / `missing_years` вычисляются в состоянии графа, но в `AgentRunResult` не попадают | матрица покрытия требует аддитивного расширения результата |
| Structure | `StructureAnalyzer` возвращает `section_matches` / `structural_changes`; `AgentRunResult.structural_changes` проброшен в рабочем дереве | в summary раздела нет `document_id`, у изменений нет ссылок на документы/evidence; сравнение содержания отсутствует (`structure_content_checked` объявлен, но не заполняется) |
| Фильтры | `SearchFilters`: `years`, `year_from/to`, `report_periods`, `issuers`, `kinds`, `section_path_prefix`, `breadcrumb_contains`, `max_section_level`, `allowed_doc_ids` | UI первого релиза показывает годы, issuer и документы; остальное — API-only |
| Корпус | один локальный индекс; список годов/документов берётся у search backend; `data/source_registry.json` пока отсутствует | переключатель корпусов в первый релиз не входит |
| Безопасность | ошибки и история очищаются от секретов; авторизации, владельцев и изоляции пользователей нет | модель владельца нужно ввести до появления HTTP-API |
| Тесты | офлайн-набор pytest, включая `tests/test_ui_helpers.py`; frontend-тестов нет | Streamlit-тесты сохраняются до этапа 5 |

### 2.5. Принятые решения

| № | Решение | Обоснование |
|---|---|---|
| D1 | `research.id` — это и есть `conversation_id` для `AgentService` | не плодим параллельную систему идентификаторов |
| D2 | Adapter — отдельное ASGI-приложение в `src/api/`, `AgentService` создаётся в процессе один раз | минимальная задержка, нет дублирования state |
| D3 | История — SQLite внутри adapter | нет внешней инфраструктуры; переживает перезапуск |
| D4 | Аутентификация — same-origin cookie; режим `local` для одного пользователя | EventSource не умеет заголовки; секреты не попадают в URL |
| D5 | Транспорт — SSE; `sequence` + `Last-Event-ID`; ограниченный replay-буфер | соответствует текущему событийному контракту |
| D6 | В сообщении хранится снимок цитат (метаданные + quote); полный текст chunk — по запросу | история не ломается после переиндексации; отдельного evidence-хранилища нет |
| D7 | Возможности backend объявляются флагами (`/api/capabilities`) | UI не изображает streaming, графики и coverage, которых нет |
| D8 | В первом релизе корпус один | переключатель корпусов — отдельная задача |

### 2.6. Зависимости от backend-спецификаций

| Возможность UI | Требуемая backend-возможность | Источник |
|---|---|---|
| Покрытие доказательствами | `CoverageReport` в `AgentRunResult` | P3, `spec_agent_enhancement.md` §4.6 |
| Числовые таблицы и графики | нормализованные `facts`, подключённые `calculations`, точки ряда (аддитивное `points[]`) | P6, §4.5 |
| Структурное сравнение | `compare_structures` / `structural_changes` с doc/year | P5 |
| Graph-панель | узлы, типизированные пути и `evidence_chunk_ids` в результате | P7 |
| Токеновый streaming | событие `answer_delta` от генератора | новое, опционально (D7) |

Если зависимость не реализована, соответствующий UI-блок не включается.
Он не заменяется догадками frontend.

## 3. Пользовательский интерфейс

### 3.1. Общая компоновка

Основной экран — рабочее пространство исследования.

**Левая панель — исследования**

- список исследований;
- история диалогов;
- создание нового исследования;
- поиск по истории;
- переименование исследования;
- удаление исследования после подтверждения;
- отображение даты последнего изменения;
- статус последнего выполнения.

**Центральная панель — диалог**

- сообщения пользователя;
- ответы агента;
- потоковая генерация ответа;
- структурированные таблицы и графики;
- ссылки на источники;
- индикатор выполнения исследования;
- поле ввода нового вопроса.

**Правая панель — контекст исследования**

- найденные документы;
- использованные разделы;
- источники доказательств;
- цитаты;
- результаты Graph Retrieval (если доступны);
- сведения о покрытии запрошенных данных;
- детали выполнения исследования.

Правая панель сворачивается и разворачивается; её состояние сохраняется в
пользовательских настройках, но не считается серверными данными.

Адаптивность:

| Ширина | Левая панель | Правая панель | Центр |
|---|---|---|---|
| ≥ 1280 px | постоянно видна | постоянно видна, сворачивается | основная область |
| 768–1279 px | выдвижная | overlay-панель | основная область |
| < 768 px | выдвижная | выдвижная | единственная основная область |

Диалог остаётся главным рабочим пространством на всех размерах.
Клавиатурная доступность: фокус в composer, `Esc` закрывает панели и диалоги,
все интерактивные элементы достижимы с клавиатуры.

### 3.2. Верхняя панель

Размещаются:

- название текущего исследования (редактируемое);
- название корпуса (в первом релизе — фиксированное, без переключателя);
- фильтр периода (годы);
- фильтр issuer и документов, если backend их публикует;
- состояние выполнения;
- кнопка создания нового исследования;
- переход в отдельный раздел Evaluation / Benchmark (см. `evaluation-webui.md`);
  раздел не смешивается с текущим исследованием и не встраивается в чат;
- пользовательские настройки интерфейса (тема, плотность, ширина панелей).

Фильтры передаются backend вместе с запросом. Frontend не применяет их к уже
полученным результатам и не «дополняет» ими ответ.

После отправки UI показывает **effective filters**, возвращённые сервером.
Если сервер сузил или изменил фильтры, над диалогом появляется предупреждение
с конкретным отличием, а не молчаливый другой результат.

### 3.3. История исследований

Исследование — отдельная пользовательская сущность.

| Поле | Назначение |
|---|---|
| `id` | UUID; одновременно `conversation_id` для `AgentService` |
| `title` | название; по умолчанию первый вопрос (обрезанный) или «Новое исследование» |
| `created_at` | дата создания |
| `updated_at` | дата последнего сообщения |
| `last_message_preview` | первый вопрос или краткое описание |
| `last_status` | `idle` / `running` / `completed` / `abstained` / `failed` / `cancelled` |
| `messages_count` | число сообщений |

Требования:

- восстановление диалога после перезагрузки страницы;
- переключение между исследованиями;
- создание нового исследования;
- удаление исследования с подтверждением;
- поиск по названию и сообщениям;
- сохранение выбранного исследования при обновлении страницы;
- корректное поведение при удалённом или чужом исследовании (404, возврат к списку).

Источник истины — backend. `localStorage` хранит только `lastResearchId` и
UI-настройки. Сообщения в `localStorage` не хранятся.

Перезагрузка страницы не теряет контекст диалога, пока процесс API жив.
Перезапуск API сохраняет видимую историю, но теряет `_conversation_history`
`AgentService`; уточняющий вопрос в этом случае обрабатывается без прошлых ходов.
Это ограничение документируется в UI-справке и не маскируется. Восстановление
контекста из БД (передача `history` в `AgentService`) — отдельная задача.

Если исследование удалено в другой вкладке, текущая вкладка при следующем запросе
получает 404 и показывает понятное состояние, не пустой экран.

## 4. Чат и взаимодействие с агентом

### 4.1. Основные возможности

Чат поддерживает:

- отправку текстовых запросов;
- потоковое получение ответа и/или этапов;
- отображение Markdown;
- таблицы;
- списки;
- код (без выполнения);
- ссылки;
- цитаты;
- структурированные блоки аналитики;
- повторную отправку запроса;
- отмену выполняющегося запроса;
- отображение ошибок.

Уточняющие вопросы продолжают контекст исследования. Каждый новый фактический
claim должен подтверждаться новыми evidence; прошлый ответ не считается источником.

### 4.2. Потоковая передача

Транспорт — Server-Sent Events. Adapter публикует один поток на `request_id`.

Публичный конверт:

```text
id: 17
event: agent
data: {"contract_version":"1","sequence":17,"type":"tool_started","request_id":"…","tool_name":"search_reports"}
```

Правила:

- `id` = монотонный `sequence` в пределах запроса;
- `event: agent` для всех событий, тип — в поле `type`;
- heartbeat — SSE-комментарий `: keep-alive` каждые 15 секунд;
- поток закрывается после терминального события;
- `Cache-Control: no-cache, no-transform`, `X-Accel-Buffering: no`.

Целевой контракт событий:

```typescript
type AgentEvent =
  | {
      type: "run_started";
      request_id: string;
      message_id: string;
    }
  | {
      type: "analysis_completed";
      request_id: string;
      intent: "factoid" | "structural" | "temporal" | "multi_hop";
      effective_filters: FilterSet;
    }
  | {
      type: "tool_started";
      request_id: string;
      tool_name: string;
      short_arguments?: Record<string, unknown>;
    }
  | {
      type: "tool_completed";
      request_id: string;
      tool_name: string;
      status: "success" | "error" | string;
      result_count?: number;
      duration_ms?: number;
    }
  | {
      type: "evidence_updated";
      request_id: string;
      evidence: EvidenceItem[];
    }
  | {
      type: "answer_started";
      request_id: string;
    }
  | {
      type: "answer_delta";
      request_id: string;
      delta: string;
    }
  | {
      type: "run_completed";
      request_id: string;
      answer_status: "answer" | "abstain";
      duration_ms: number;
      message: ChatMessage;
    }
  | {
      type: "run_failed";
      request_id: string;
      code: string;
      message: string;
      retryable: boolean;
    }
  | {
      type: "run_cancelled";
      request_id: string;
    };
```

`evidence_updated` и `answer_delta` — **опциональные** события. Adapter объявляет
их поддержку в `/api/capabilities` (`token_streaming`, `incremental_evidence`) и
передаёт только тогда, когда backend реально их публикует.

Сопоставление с текущим backend:

| Событие backend | Публичное событие | Примечание |
|---|---|---|
| `run_started` | `run_started` | adapter добавляет `message_id` |
| `analysis_completed` | `analysis_completed` | `effective_filters` сериализуется |
| `tool_started` | `tool_started` | `short_arguments` уже очищены backend |
| `tool_completed` | `tool_completed` | `status`, `result_count`, `duration_ms` |
| `answer_started` | `answer_started` | — |
| `answer_delta` | `answer_delta` | сейчас не публикуется |
| `run_completed` | `run_completed` | `result` превращается в `message` + evidence |
| `run_failed` | `run_failed` | `error_code` → `code`, `retryable` выставляет adapter |
| — | `evidence_updated` | сейчас не публикуется |
| — | `run_cancelled` | добавляется при отмене |
| — | heartbeat | только adapter |

Запрещено:

- изображать посимвольную печать, если `answer_delta` не приходит;
- показывать «этап», который не следует из полученного события;
- пересылать `filters` целиком в `short_arguments` или раскрывать query.

Если потоковой генерации нет, UI показывает состояние «Агент готовит ответ»
и атомарно отображает финальный `message` из `run_completed`.

### 4.3. Требования к обработке событий

- Все события одного запроса имеют одинаковый `request_id`.
- События поступают в порядке возрастания `sequence`.
- События с `sequence` не больше последнего обработанного игнорируются.
- События другого `request_id` игнорируются.
- После `run_completed` / `run_failed` / `run_cancelled` поток не обрабатывается.
- Повторное подключение с `Last-Event-ID` не дублирует уже обработанные фрагменты.
- Завершение запроса всегда имеет терминальное событие.
- Ошибка отображается пользователю с `code` и `request_id`, а не только в консоли.
- При разрыве соединения UI переходит в состояние «переподключение», а не
  показывает вечный spinner.
- Если запрос невозможно воспроизвести (перезапуск API), UI получает
  `resync`/`410` и загружает сохранённое сообщение либо показывает
  «выполнение прервано».

### 4.4. Отображение процесса исследования

Пользователю показываются понятные этапы:

1. Анализ запроса.
2. Поиск информации.
3. Проверка найденных данных.
4. Сопоставление результатов.
5. Подготовка ответа.

Этап определяется по полученному событию и текущему статусу, а не по таймеру.
Текст этапа может быть агрегированным, но не выдуманным.

В панели «Ход исследования» разрешается показывать:

- вызванные инструменты;
- очищенные аргументы поиска;
- найденные документы;
- число найденных фрагментов;
- длительность;
- результаты проверки и предупреждения;
- причину продолжения или завершения исследования, если backend её передал;
- retrieval-диагностику, если она опубликована (P1 в `spec_agent_enhancement.md`).

Нельзя показывать скрытые рассуждения модели, prompt целиком, сырые секреты,
полный текст корпуса или «прогресс», не связанный с событиями.

## 5. Evidence Panel — источники и доказательства

Это один из наиболее важных элементов интерфейса. Ответ должен быть связан с
исходными документами, а не существовать отдельно от них.

### 5.1. Карточка источника

Карточка содержит:

- название документа (`document_title`);
- год документа;
- issuer;
- название раздела;
- путь раздела;
- страницу или диапазон страниц, если доступно;
- метку страницы;
- идентификатор chunk;
- фрагмент исходного текста (quote);
- тип источника: текст или таблица.

Если поле отсутствует в данных, интерфейс показывает «не указано» и не
подставляет догадку. Для 2015 года issuer обязателен: это БПС-Сбербанк
(Беларусь), а не ПАО Сбербанк; скрывать issuer нельзя.

### 5.2. Связь ответа с источником

При нажатии на цитату:

- открыть правую панель и выбрать источник;
- показать исходный фрагмент;
- показать документ и раздел;
- показать страницу PDF, если она известна;
- выделить фрагмент, если доступен полный текст chunk и quote в нём находится.

Если полный текст недоступен, показывается только `quote` и метаданные.
Если quote не передан, показывается «цитата не предоставлена», а не текст
соседнего chunk.

Ссылка на PDF-страницу — опциональная возможность (см. `/api/documents/{doc_id}/file`).
Встроенный PDF-вьюер с подсветкой координат не входит в первый релиз: координат
в `Answer` нет.

### 5.3. Модель EvidenceItem

```typescript
interface EvidenceItem {
  evidence_id: string;          // = chunk_id; ключ навигации UI
  chunk_id: string;
  document_id: string;
  document_title?: string;
  issuer?: string;
  year?: number;
  section_title?: string;
  section_path?: string[];
  page_start?: number;
  page_end?: number;
  page_label?: string;
  excerpt: string;              // = Citation.quote, может быть ""
  source_type?: "text" | "table";
  has_full_text: boolean;       // доступен ли /api/evidence/{chunk_id}
}
```

Это минимальный целевой контракт. Соответствие фактическим полям `Citation`:

| EvidenceItem | Источник | Правило |
|---|---|---|
| `evidence_id` | `Citation.chunk_id` | не использовать `chunk.evidence_id` — это идентификатор страницы, не chunk |
| `chunk_id` | `Citation.chunk_id` | — |
| `document_id` | `Citation.doc_id` | `null` допустим только если backend его не передал |
| `document_title` | `chunk.title` через resolver | не выводить из `doc_id` |
| `issuer` | `Citation.issuer` | обязателен для корпуса с 2015 |
| `year` | `Citation.year` | не выводить из текста |
| `section_title` | последний сегмент `Citation.section_path` | `section_path` в backend — строка через `/` |
| `section_path` | `Citation.section_path.split("/")` | пустые сегменты отбросить |
| `page_start` | `Citation.page_pdf` | — |
| `page_end` | — | сейчас не передаётся; `undefined` |
| `page_label` | `Citation.page_label` | — |
| `excerpt` | `Citation.quote` | `null` → `""` |
| `source_type` | `chunk.kind` через resolver | `text` / `table` |
| `has_full_text` | результат resolver | `false`, если endpoint недоступен |

### 5.4. Покрытие доказательствами

Если агент анализирует несколько лет или показателей, интерфейс отображает
матрицу покрытия. Статусы приходят из `CoverageReport`
(`spec_agent_enhancement.md` §4.6):

| Показатель | 2020 | 2021 | 2022 | 2023 | 2024 |
|---|---|---|---|---|---|
| Выручка | Найдено | Год отсутствует | Найдено | Найдено | Найдено |
| Чистая прибыль | Найдено | Год отсутствует | Не найдено | Найдено | Найдено |
| Активы | Найдено | Год отсутствует | Найдено | Найдено | Найдено |

Статусы:

| Код | Подпись | Значение |
|---|---|---|
| `covered` | Найдено | значение подтверждено источником |
| `not_found` | Не найдено | год есть в корпусе, показатель не найден поиском |
| `year_absent` | Год отсутствует в корпусе | отчёта за этот год нет |

Требования:

- `not_found` не означает «показателя нет в отчёте»; это формулируется в tooltip;
- `year_absent` не отображается как ноль или пустая ячейка;
- отсутствие доказательства не выдаётся за отсутствие показателя;
- клик по ячейке показывает связанные evidence (`cell_evidence`) или пустое состояние с причиной;
- статус `CoverageReport.status` (`not_required`/`complete`/`partial`/`insufficient`)
  показывается отдельным баннером, а не смешивается с цветом ячеек.

Frontend не вычисляет покрытие самостоятельно. Если `coverage` отсутствует,
блок не отображается.

### 5.5. Endpoint источника

```text
GET /api/evidence/{chunk_id}
```

Ответ:

```json
{
  "chunk_id": "sber_2023:00078:c3:c5cc6e1f46e2",
  "document_id": "sber_2023",
  "document_title": "Годовой отчёт 2023",
  "issuer": "ПАО Сбербанк",
  "year": 2023,
  "section_path": ["Стратегия", "Ключевые показатели"],
  "page_start": 12,
  "page_label": "12",
  "source_type": "text",
  "text": "…",
  "html": null
}
```

Правила:

- источник — существующий chunk backend (`AgentTools` / `ChunkBackend`), не новое хранилище;
- чанк ищется только по ID из известного индекса;
- для таблиц возвращается `html` и `source_type: "table"`;
- неизвестный ID → 404, без обхода каталогов и файловой системы;
- ответ кэшируется как `private, max-age=…`, но не публично;
- полный текст не хранится в истории сообщений.

## 6. Аналитические представления

### 6.1. Таблицы

Таблицы — полноценные интерактивные компоненты.

Требования:

- сортировка;
- изменение ширины колонок;
- прокрутка;
- закрепление заголовка;
- форматирование чисел;
- выделение важных значений;
- экспорт в CSV;
- переход от значения к источнику.

Для числовых таблиц отображаются единицы измерения.

Нельзя смешивать значения в рублях, миллионах рублей и миллиардах рублей.
Группировка выполняется по паре `(metric, unit)`; если `unit` не указан,
таблица помечается «единица не указана» и сравнительный блок не строится.

В первом релизе источником строк служат нормализованные `facts` и `calculations`
backend. Frontend не пересчитывает значения, а только раскладывает их по колонкам.
CSV-экспорт — сериализация отображаемых данных, а не новый расчёт.

### 6.2. Графики

Используется Recharts.

Поддерживаются:

- линейные графики;
- столбчатые диаграммы;
- группированные столбцы;
- сравнение нескольких показателей;
- абсолютные и относительные изменения (значения приходят с backend).

Обязательные элементы:

- подписи осей;
- единицы измерения;
- легенда;
- tooltip;
- точные значения;
- переход к доказательству для точки;
- корректная обработка пропусков.

Пропуск в ряду — разрыв линии или отсутствующая точка, а не ноль.
Разные единицы не объединяются в один график.

Контракт данных (аддитивное расширение `calculations` из P6):

```typescript
interface SeriesPoint {
  year: number;
  value: number;
  evidence_ids: string[];
}

interface CalculationSeries {
  metric: string;
  metric_label?: string;
  unit: string;
  points: SeriesPoint[];
  from_year: number;
  to_year: number;
  absolute_change: number;
  percent_change?: number | null;
  cagr?: number | null;
  direction: "increase" | "decrease" | "flat";
  warnings?: string[];
}
```

Если backend не передаёт `points`, график для этого показателя не строится:
показывается таблица и пояснение. Фронтенд не «дорисовывает» ряд из
`from_value`/`to_value`.

CAGR, процент и разницу считает только backend (`src/engine/calculations.py`).
UI помечает их как расчёт, а не как факт из отчёта.

### 6.3. Структурное сравнение годовых отчётов

Отдельное представление для сравнения структуры документов.

Отображаются:

- добавленные разделы;
- разделы, не обнаруженные в более позднем отчёте;
- переименованные разделы;
- перемещённые / изменённые по уровню;
- разделы с изменившимся объёмом;
- стабильные разделы.

Фактические типы `structural_changes` (`src/engine/structure_compare.py`):

| `change_type` | Подпись UI | Условие |
|---|---|---|
| `stable` | Без изменений | заголовок, родитель и уровень совпадают |
| `added` | Добавлен | найден только в более позднем отчёте |
| `removed` | Не обнаружен в более позднем отчёте | найден только в раннем |
| `renamed` | Переименован | изменился заголовок |
| `restructured` | Перемещён / изменён уровень | изменился родитель или уровень |
| `expanded` | Объём вырос | вырос page span раздела |
| `reduced` | Объём сократился | уменьшился page span раздела |

Поля элемента: `from_year`, `to_year`, `from_section`, `to_section`, `score`,
`change_type`, `detail`. Раздел содержит `title`, `section_path`, `level`,
`page_start`, `page_end`.

Пример:

| Раздел | 2022 | 2023 | Изменение |
|---|---|---|---|
| Стратегия | Есть | Есть | Без изменений |
| ESG | Нет | Есть | Добавлен |
| Управление рисками | Есть | Есть | Перемещён / изменён уровень |
| Корпоративное управление | Есть | Не обнаружен | Не обнаружен в более позднем отчёте |

Требования и ограничения:

- сравнение отображается попарно (`from_year` → `to_year`);
- «стабилен» показывается только для пары, где backend вернул `stable`;
  UI не выводит «стабилен все годы» самостоятельно;
- «не обнаружен» не равно «удалён»: при отсутствии артефакта структуры
  показывается предупреждение `structure_unavailable` / `structure_scope_limited`;
- разделение и объединение разделов **не поддерживаются** текущим анализатором;
  UI не должен показывать эти категории;
- изменение заголовка и изменение содержания — разные вещи. Сравнение содержания
  сейчас не реализовано (`structure_content_checked` не заполняется), поэтому
  вкладка «Содержание» либо отсутствует, либо показывает честное пустое состояние
  до появления backend-контракта;
- для каждого изменения отображаются годы, исходные названия, документы
  (`document_id`/`year`), страницы и краткое описание (`detail`);
- ссылки на evidence обязательны, если UI утверждает переименование/перенос;
  сейчас `structural_changes` не содержит `chunk_id`, поэтому Stage 4 включает
  минимальное обогащение результата (`document_id`, `year`, при наличии —
  `evidence_chunk_ids`). Без этого кнопка «Открыть доказательство» не показывается.

### 6.4. Результаты Graph Retrieval

Если backend возвращает результаты графового поиска, интерфейс может отображать:

- найденные сущности;
- связи между ними;
- связанные документы;
- подтверждающие фрагменты.

Визуализация графа — дополнительная возможность, а не обязательная часть первого
релиза. Текущий `AgentRunResult` не содержит узлов и путей, поэтому панель
включается только после P7 и публикации контракта.

Нельзя показывать обнаруженную связь как подтверждённый факт без доступного
первичного evidence. Ребро без `evidence_chunk_ids` отображается как
«связь без подтверждения» или не отображается вовсе.

## 7. API-контракт

API не зависит от React-компонентов. База — `/api`. Несовместимые изменения
выпускаются как `/api/v2`; скрытых breaking changes нет.

### 7.1. Общие требования

- единый формат ошибок;
- обязательная проверка доступа к исследованию;
- валидация входных данных;
- идентификаторы запросов;
- корректная обработка повторных запросов;
- ограничение размера передаваемых данных;
- отсутствие секретов и внутренних настроек в frontend;
- версионирование контракта;
- timestamps в ISO 8601 UTC;
- идентификаторы — UUID строкой;
- snake_case в JSON;
- неизвестные поля клиента игнорируются, неизвестные поля ответа не ломают UI.

### 7.2. Endpoint

| Метод | Путь | Назначение | Этап |
|---|---|---|---|
| GET | `/api/health` | готовность adapter и корпуса | 1 |
| GET | `/api/capabilities` | флаги возможностей | 1 |
| GET | `/api/corpus` | годы, документы, issuers | 1 |
| GET | `/api/research` | список исследований, `q`, `limit`, `offset` | 1 |
| POST | `/api/research` | создать исследование | 1 |
| GET | `/api/research/{research_id}` | карточка исследования | 1 |
| PATCH | `/api/research/{research_id}` | переименовать | 1 |
| DELETE | `/api/research/{research_id}` | удалить исследование | 1 |
| GET | `/api/research/{research_id}/messages` | история сообщений | 1 |
| POST | `/api/research/{research_id}/messages` | отправить вопрос | 1 |
| GET | `/api/requests/{request_id}` | статус и терминальный результат | 1 |
| GET | `/api/requests/{request_id}/events` | SSE-поток | 1 |
| POST | `/api/requests/{request_id}/cancel` | отмена | 5 |
| GET | `/api/evidence/{chunk_id}` | метаданные и текст chunk | 2 |
| GET | `/api/documents/{doc_id}/file` | PDF для перехода на страницу | 2, опционально |

Не создавать endpoint для каждой внутренней функции агента.

Evaluation endpoints (`/api/evaluation/*`) не дублируются здесь: их контракт,
хранение и очередь описаны в `evaluation-webui.md`. Общий `/api/capabilities`
публикует только флаги доступности раздела.

### 7.3. Исследования

`GET /api/research?q=...` возвращает:

```json
{
  "items": [
    {
      "id": "…",
      "title": "Динамика чистой прибыли",
      "created_at": "2026-11-14T10:00:00Z",
      "updated_at": "2026-11-14T10:05:00Z",
      "last_message_preview": "Какая чистая прибыль за 2023 год?",
      "last_status": "completed",
      "messages_count": 4
    }
  ],
  "total": 1,
  "next_offset": null
}
```

Правила:

- поиск по названию и тексту сообщений (case-insensitive);
- сортировка по `updated_at` убыванию;
- `limit` по умолчанию 50, максимум 200;
- чужое/несуществующее исследование → 404 (не 403), чтобы не раскрывать существование;
- `DELETE` удаляет сообщения и запросы каскадно;
- `PATCH` принимает только `title` (1–200 символов после trim).

### 7.4. Сообщения

`POST /api/research/{research_id}/messages`

```json
{
  "content": "Сравни выручку за 2020–2024",
  "client_message_id": "4d1c…",
  "filters": {
    "years": [2020, 2021, 2022, 2023, 2024],
    "issuers": ["ПАО Сбербанк"],
    "allowed_doc_ids": []
  }
}
```

Ответ — `202 Accepted`:

```json
{
  "request_id": "…",
  "user_message": { "id": "…", "role": "user", "content": "…", "status": "completed" },
  "assistant_message_id": "…",
  "events_url": "/api/requests/…/events",
  "research": { "id": "…", "updated_at": "…" }
}
```

Правила:

- `content`: 1–16 000 символов после trim;
- `client_message_id` обязателен и уникален в пределах исследования (идемпотентность);
- повторный POST с тем же `client_message_id` возвращает существующий `request_id`
  и не запускает второй прогон;
- одновременно у исследования допускается один активный запрос; второй POST
  получает `409 request_in_progress` и `request_id` активного запроса;
- активные фильтры сохраняются в запросе и передаются в `AgentService.ask/stream`;
- пустые значения фильтров не передаются;
- невалидный тип фильтра → `422 validation_error`, без «умной» нормализации на клиенте;
- пользовательское сообщение сохраняется до запуска агента;
- assistant-сообщение создаётся со статусом `streaming` и обновляется по терминальному событию.

`GET /api/research/{research_id}/messages?limit=&before=` возвращает сообщения
в хронологическом порядке, включая снимок evidence и аналитики. Пагинация —
по `created_at`/`id`, без пропусков при одинаковых timestamp.

### 7.5. Поток событий

`GET /api/requests/{request_id}/events`

- `Accept: text/event-stream`;
- проверка владельца исследования, к которому относится запрос;
- replay по `Last-Event-ID`, если `sequence` ещё в буфере;
- буфер ограничен (например, 1 000 событий или 10 минут); точный лимит — конфигурация;
- если запрос завершён и события в буфере — отдать остаток и закрыть поток;
- если replay невозможен — `event: resync` с `reason` и закрытие; UI загружает
  сообщения через REST;
- если запрос неизвестен/просрочен — `410 request_not_replayable`;
- SSE не содержит секретов, prompt и полного текста корпуса.

`GET /api/requests/{request_id}` — REST-fallback для переподключения:

```json
{
  "request_id": "…",
  "status": "running",
  "message_id": "…",
  "message": null,
  "error": null
}
```

Для терминального запроса возвращается сохранённый `message` (или `error`),
чтобы UI мог восстановиться без replay.

### 7.6. Отмена

`POST /api/requests/{request_id}/cancel`

Семантика:

1. Adapter атомарно помечает запрос `cancelled`.
2. Вызывается `AgentService.cancel(request_id)`; граф проверяет флаг отмены на
   границах узлов (`choose_action`, `harvest_tool_result`, `assess_evidence`,
   `generate_answer`).
3. Поток событий завершается `run_cancelled`.
4. Результат прогона не сохраняется как ответ; сообщение получает статус `cancelled`.
5. Повторная отмена идемпотентна; отмена завершённого запроса — no-op `200`.
6. Провайдерский LLM-вызов может завершиться уже после отмены; его результат
   отбрасывается. UI показывает «останавливается…» до `run_cancelled` и не
   выдаёт частичный ответ за готовый.

Отмена, которая только скрывает spinner, запрещена.

### 7.8. Ошибки

```json
{
  "error": {
    "code": "request_in_progress",
    "message": "В исследовании уже выполняется запрос.",
    "request_id": "…",
    "retryable": true,
    "details": { "active_request_id": "…" }
  }
}
```

| Код | HTTP | Значение |
|---|---|---|
| `validation_error` | 422 | невалидный payload/фильтр |
| `not_found` | 404 | исследование/сообщение/источник не найден |
| `request_in_progress` | 409 | уже есть активный запрос |
| `request_not_found` | 404 | неизвестный request_id |
| `request_not_replayable` | 410 | события недоступны после перезапуска |
| `payload_too_large` | 413 | превышен размер сообщения/ответа |
| `rate_limited` | 429 | превышен лимит запросов |
| `backend_unavailable` | 503 | `AgentService`/корпус/LLM недоступны |
| `internal_error` | 500 | непредвиденная ошибка без traceback |

Внешний текст ошибки не содержит prompt, stack trace, ключей и тел ответов провайдера.
`request_id` присутствует везде, где он существует.

### 7.9. Минимальная персистентность

```sql
CREATE TABLE researches (
  id TEXT PRIMARY KEY,
  owner_id TEXT NOT NULL,
  title TEXT NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE TABLE messages (
  id TEXT PRIMARY KEY,
  research_id TEXT NOT NULL REFERENCES researches(id) ON DELETE CASCADE,
  role TEXT NOT NULL CHECK (role IN ('user', 'assistant')),
  content TEXT NOT NULL DEFAULT '',
  status TEXT NOT NULL,
  request_id TEXT,
  client_message_id TEXT,
  answer_json TEXT,           -- citations + facts + calculations + structural_changes + warnings
  filters_json TEXT,          -- effective filters запроса
  error_json TEXT,
  created_at TEXT NOT NULL
);

CREATE TABLE requests (
  id TEXT PRIMARY KEY,
  research_id TEXT NOT NULL REFERENCES researches(id) ON DELETE CASCADE,
  assistant_message_id TEXT NOT NULL,
  status TEXT NOT NULL,       -- queued|running|completed|abstained|failed|cancelled
  error_code TEXT,
  started_at TEXT NOT NULL,
  finished_at TEXT
);

CREATE UNIQUE INDEX ux_messages_client
  ON messages(research_id, client_message_id)
  WHERE client_message_id IS NOT NULL;
```

Правила:

- SQLite в WAL-режиме, `PRAGMA foreign_keys = ON`, миграции при старте, без ORM;
- в `answer_json` — только данные, которые уже вернул `Answer`/`AgentRunResult`;
- полный текст chunk и HTML таблиц в БД не дублируются;
- при старте `running`-запросы помечаются `failed` с `code=interrupted`, чтобы UI не висел;
- удаление исследования каскадное;
- секреты, prompt и env не сохраняются;
- автоматическая очистка истории в первом релизе не требуется, но настройка retention
  должна быть предусмотрена конфигурацией.

### 7.10. Сериализация backend-контрактов

Adapter сериализует dataclasses `AgentEvent`, `Answer`, `Citation`,
`AgentRunResult`, `ToolEvent`, `SearchFilters` и не пересобирает их поля.
Правила:

- `Answer.calculations` и `AgentRunResult.calculations` не теряются;
- `AgentRunResult.structural_changes` пробрасывается в `message.analysis`;
- `effective_filters` возвращается в событии `analysis_completed` и в сообщении;
- `warnings` — массив строковых кодов, не локализованный текст;
- локализация — на frontend по словарю кодов с fallback на сам код.

## 8. Состояние frontend

Frontend разделяет:

1. Состояние приложения.
2. Состояние текущего исследования.
3. Состояние диалога.
4. Состояние выполняющегося запроса.
5. Состояние отображения источников и аналитики.

Сущности:

```typescript
interface Research {
  id: string;
  title: string;
  created_at: string;
  updated_at: string;
  last_message_preview?: string;
  last_status: ResearchStatus;
  messages_count: number;
}

type ResearchStatus =
  | "idle" | "running" | "completed" | "abstained" | "failed" | "cancelled";

interface ChatMessage {
  id: string;
  research_id: string;
  role: "user" | "assistant";
  content: string;
  created_at: string;
  status: "pending" | "streaming" | "completed" | "abstained" | "failed" | "cancelled";
  request_id?: string;
  effective_filters?: FilterSet;
  evidence: EvidenceItem[];
  analysis?: AnalysisResult;
  warnings: string[];
  error?: { code: string; message: string; retryable: boolean };
}

interface AnalysisResult {
  calculations: CalculationSeries[];
  facts: Fact[];
  coverage?: CoverageReport;
  structural_changes?: StructuralChange[];
}

interface Fact {
  metric: string;
  metric_label?: string;
  year: number;
  value: string | number;
  unit?: string;
  scale?: string;
  chunk_id: string;
  row_label?: string;
  column_label?: string;
}

type CoverageStatus = "covered" | "not_found" | "year_absent";

interface CoverageReport {
  status: "not_required" | "complete" | "partial" | "insufficient";
  expected_years: number[];
  covered_years: number[];
  missing_years: number[];
  metrics: Record<string, Record<string, CoverageStatus>>;
  // evidence по ячейке; аддитивное требование к backend (этап 3)
  cell_evidence?: Record<string, Record<string, string[]>>;
  missing_metrics: string[];
  notes: string[];
}

interface SectionSummary {
  title?: string;
  section_path?: string;
  level?: number;
  page_start?: number;
  page_end?: number;
}

interface StructuralChange {
  from_year: number;
  to_year: number;
  from_section?: SectionSummary;
  to_section?: SectionSummary;
  change_type:
    | "stable" | "added" | "removed"
    | "renamed" | "restructured" | "expanded" | "reduced";
  score?: number;
  detail?: string;
  document_id?: string;
  evidence_chunk_ids?: string[];
}

interface FilterSet {
  years?: number[];
  year_from?: number;
  year_to?: number;
  issuers?: string[];
  allowed_doc_ids?: string[];
  kinds?: Array<"text" | "table">;
}
```

Правила:

- серверные данные — TanStack Query (`research`, `messages`, `evidence`);
- streaming-буфер запроса живёт вне общего store: `useRef` + reducer на запрос;
- частота обновлений текста не должна перерисовывать весь список сообщений;
- выбранное исследование и настройки панелей — лёгкий UI-context;
- не помещать всё состояние в один глобальный объект;
- не использовать `localStorage` для сообщений;
- после терминального события инвалидировать `messages` и карточку исследования;
- при `resync`/410 перезагрузить сообщения и показать честный статус.

Состояние запроса:

```text
idle → submitting → streaming → completed
                             ├→ abstained
                             ├→ failed
                             └→ cancelling → cancelled
```

Недопустимые переходы игнорируются, а не «исправляются» угадыванием.

## 10. Backend Adapter

API/Streaming Adapter — тонкий слой между frontend и существующим Agent_RAG.

Задачи:

- принять запрос;
- проверить идентификаторы и права доступа;
- восстановить или создать контекст исследования;
- передать запрос существующему `AgentService`;
- преобразовать события агента в публичный API-контракт;
- передавать evidence и структурированные результаты;
- обрабатывать отмену;
- возвращать ошибки в стандартизированном виде;
- хранить историю исследований и сообщений.

Запрещается:

- дублировать `AgentService`;
- повторно реализовывать retrieval;
- реализовывать собственную генерацию ответа;
- создавать второй независимый механизм управления агентом;
- переносить бизнес-правила в API-контроллеры.

Предлагаемая структура:

```text
src/api/
├── app.py          # FastAPI application, lifespan, CORS, auth
├── routes/
│   ├── research.py
│   ├── messages.py
│   ├── events.py
│   └── evidence.py
├── schemas.py      # Pydantic-модели публичного контракта
├── serialize.py    # dataclass → JSON, маппинг Citation → EvidenceItem
├── store.py        # SQLite: researches, messages, requests
├── auth.py         # owner_id, cookie/session, режим local
├── streaming.py    # SSE pump, replay buffer, cancel registry
├── services.py     # ленивая инициализация AgentService, corpus info
└── config.py       # env adapter'а
```

Требования к реализации:

- `AgentService` создаётся один раз в lifespan; импорт `src.api.app` не читает
  env и не строит индексы;
- `AgentTools`/retrieval остаются в Python-ядре;
- SSE pump не блокирует event loop: синхронный итератор выполняется в threadpool
  или перекладывается в asyncio-очередь;
- при недоступном корпусе `/api/health` возвращает 503, а чат — понятную ошибку;
- adapter не добавляет события, которых не было в backend, кроме heartbeat,
  `run_cancelled`, `resync` и назначения `message_id`;
- отмена реализуется через `AgentService.cancel(request_id)` и проверку флага
  в узлах графа; это аддитивное изменение `AgentService`, а не новый workflow;
- если существующий backend не поддерживает streaming, используется `ask()` и
  публикуется только `run_started`/`run_completed`; контракт остаётся тем же.

Запуск:

```bash
uvicorn src.api.app:app --port 8000
```

Добавление `fastapi` и `uvicorn` в `requirements.txt` — часть этапа 1.

## 11. Безопасность и надёжность

Обязательные требования:

- серверная проверка доступа к каждому исследованию;
- изоляция данных пользователей;
- запрет доступа к чужим сообщениям и evidence;
- валидация всех API-параметров;
- ограничение размера сообщений и событий;
- корректная обработка разрыва соединения;
- отсутствие API-ключей и внутренних секретов в frontend;
- безопасный рендеринг Markdown и HTML;
- запрет выполнения произвольного HTML из ответа агента;
- защита от повторной отправки одного запроса;
- корректное восстановление после перезагрузки страницы.

Конкретизация:

| Область | Правило |
|---|---|
| Аутентификация | `AUTH_MODE=local` в первом релизе: один локальный владелец; cookie `HttpOnly`, `SameSite=Lax`, `Secure` в HTTPS. SSO/провайдеры — вне объёма |
| Владение | каждая выборка и мутация фильтруется по `owner_id`; тест на чужой `research_id` обязателен |
| CSRF | same-origin + `SameSite`; POST из чужого Origin отклоняется |
| CORS | dev — только `http://localhost:5173` с credentials; production — same-origin |
| EventSource | cookie, не query-token; токены не логируются |
| Markdown | `react-markdown` + `remark-gfm` + `rehype-sanitize`; raw HTML запрещён |
| Ссылки | внешние — `rel="noopener noreferrer"`, `target="_blank"` |
| HTML таблиц | только из `/api/evidence`; санитизация; без inline-скриптов |
| Лимиты | сообщение ≤ 16 000 символов; событие ≤ 256 КБ; ответ evidence ≤ 1 МБ |
| Дубли | `client_message_id` + unique index; повтор не запускает второй прогон |
| Перезапуск | `running` → `failed(interrupted)`; UI предлагает повторить |
| Логи | request_id, код ошибки, длительность; без prompt, chunk-текста и ключей |
| Ошибки | без traceback и текста провайдера; fallback-сообщение + код |
| Rate limit | минимум на POST-сообщения; лимит конфигурируется |

повторная отправка не создаёт дубль; SSE не блокирует сервер.

Токеновый streaming не обязателен, если backend его не поддерживает. В этом
случае `capabilities.token_streaming = false`, а UI не имитирует печать.

Streamlit-чат остаётся рабочим до этапа 5. Существующие тесты
`tests/test_ui_helpers.py` не удаляются и не переписываются под новый UI.

Раздел Evaluation / Benchmark реализуется отдельным этапом после базового WebUI и
API; его контракт, очередь и экраны описаны в `evaluation-webui.md`. Он не входит
в обязательный объём этапа 1 и не блокирует запуск чата.

### Этап 2. Evidence и источники

Реализовать:

- правую панель источников;
- карточки evidence;
- цитаты в ответах;
- переход от цитаты к источнику;
- отображение документа, раздела, страницы, issuer и chunk;
- endpoint `/api/evidence/{chunk_id}`;
- обработку недоступных источников.

Критерий готовности: каждое переданное backend доказательство доступно
пользователю и связано с соответствующим ответом; неизвестные метаданные
показываются честно, без выдуманных страниц и названий.

### Этап 3. Аналитические представления

Реализовать:

- интерактивные таблицы;
- графики;
- отображение числовых показателей и единиц;
- переход от значения к источнику;
- экспорт таблиц в CSV;
- состояния «нет данных», «единица не указана», «расчёт недоступен».

Зависимость: P6 в `spec_agent_enhancement.md` (facts + calculations + `points`).

Критерий готовности: агент возвращает структурированный аналитический результат,
а UI корректно его отображает без повторного анализа данных; разные единицы
никогда не смешиваются.

### Этап 4. Структурное сравнение

Реализовать специализированное представление:

- сравнение структуры отчётов;
- изменения разделов;
- сравнение содержания (только при наличии backend-контракта);
- переход к исходным разделам и доказательствам.

Зависимость: P5 в `spec_agent_enhancement.md`, плюс минимальное обогащение
`structural_changes` полями `document_id`, `year` и, при наличии,
`evidence_chunk_ids`.

Критерий готовности: пользователь может просмотреть структурные изменения между
выбранными годами и проверить их по исходным документам; раздел не называется
«удалённым» без доступной структуры; категории split/merge и изменение содержания
не показываются, пока backend их не поддерживает.

### Этап 5. Полировка и отказ от Streamlit

Реализовать:

- адаптивную компоновку;
- состояния загрузки и ошибок;
- отмену запросов на backend;
- восстановление соединения;
- доступность интерфейса;
- оптимизацию длинных диалогов;
- проверку производительности;
- удаление Streamlit UI и его зависимостей.

Streamlit удаляется только после того, как все обязательные пользовательские
сценарии проходят через новый UI и E2E-набор зелёный.

## 13. Тестирование

### 13.1. Backend contract tests

- Pydantic-схемы запросов/ответов и коды ошибок.
- Владелец: чужой `research_id` → 404; каскадное удаление.
- `client_message_id`: повторный POST не создаёт второй прогон.
- Один активный запрос на исследование → 409.
- SSE: порядок `sequence`, `Last-Event-ID`, терминальное событие, heartbeat.
- Replay после завершения; `410` после «перезапуска».
- Отмена: статус, `run_cancelled`, отсутствие сохранённого ответа.
- Сериализация: `Answer.calculations`, `structural_changes`, `effective_filters`
  не теряются.
- `interrupted` при старте для зависших `running`.
- `/api/evidence`: 404, таблица, метаданные, отсутствие path traversal.
- Лимиты payload.
- Тесты используют fake `AgentService`/fake tools; сеть и LLM не нужны.

### 13.2. Frontend unit/component tests

- отображение сообщений и Markdown;
- санитизация HTML и ссылок;
- обновление потокового ответа;
- обработка `sequence`, дублей, чужого `request_id`;
- завершение, ошибка, отмена;
- отображение evidence;
- корректность таблиц и графиков;
- разные единицы не объединяются;
- отсутствующее значение не превращается в ноль;
- `year_absent` / `not_found` различаются;
- structure: подписи типов, отсутствие split/merge;
- доступность: роли, фокус, клавиатура.

### 13.3. Integration tests

- создание исследования;
- отправка сообщения;
- получение SSE;
- завершение запроса;
- восстановление истории;
- переход к источнику;
- отображение аналитического результата;
- переподключение после разрыва.

### 13.4. End-to-end tests

Обязательные сценарии:

1. Пользователь создаёт новое исследование.
2. Отправляет простой вопрос.
3. Получает потоковый ответ (или этапы + финальный ответ).
4. Открывает источник из ответа.
5. Задаёт уточняющий вопрос.
6. Перезагружает страницу и восстанавливает диалог.
7. Запрашивает сравнение показателя за несколько лет.
8. Открывает таблицу и график; проверяет единицы.
9. Запрашивает сравнение структуры отчётов.
10. Отменяет длительный запрос.
11. Получает корректное сообщение об ошибке при недоступности backend.
12. Повторно отправляет запрос и не создаёт дубль.

Тесты используют контролируемые backend fixtures и реальные контракты API.
Проверять только визуальный рендеринг без взаимодействия с backend запрещено.

## 14. Критерии приёмки

- [ ] React WebUI запускается независимо от Streamlit.
- [ ] Backend RAG-ядро используется без переписывания.
- [ ] Frontend не импортирует Streamlit и не содержит retrieval/generation.
- [ ] `research.id` совпадает с `conversation_id`; параллельной системы ID нет.
- [ ] Пользователь может создавать, переименовывать, удалять и переключать исследования.
- [ ] История восстанавливается после перезагрузки страницы из backend.
- [ ] Выбранное исследование восстанавливается после перезагрузки.
- [ ] Этапы исследования отображаются по реальным событиям.
- [ ] Потоковая генерация не имитируется, если backend её не поддерживает.
- [ ] Отмена останавливает доставку результата на backend и не сохраняет ответ.
- [ ] Ошибки отображаются с кодом и `request_id`, без traceback.
- [ ] Повторная отправка сообщения не создаёт дубль.
- [ ] Evidence отображаются и доступны из ответа.
- [ ] Источник содержит доступные метаданные документа, раздела, страницы и issuer.
- [ ] Недоступные метаданные не выдумываются.
- [ ] Таблицы отображают числовые данные и единицы измерения.
- [ ] Разные единицы не смешиваются.
- [ ] Графики отображают только данные backend; пропуски не становятся нулями.
- [ ] Значения можно связать с источниками.
- [ ] Структурные изменения отчётов отображаются попарно и без ложных категорий.
- [ ] Покрытие использует статусы backend (`covered`/`not_found`/`year_absent`).
- [ ] Данные пользователей изолированы проверкой владельца.
- [ ] Markdown/HTML санитизируются; произвольный HTML не исполняется.
- [ ] Основные пользовательские сценарии покрыты E2E-тестами.
- [ ] Streamlit не удаляется до успешного прохождения приёмки.

## 15. Что не входит в объём

В рамках этой задачи не следует:

- переписывать `AgentService`;
- заменять LangGraph;
- переписывать `HybridRetriever`;
- менять алгоритмы Graph RAG;
- вводить новый Research Engine;
- создавать отдельную систему хранения evidence;
- переносить обработку документов в frontend;
- добавлять новые LLM-механизмы только ради интерфейса;
- создавать сложную систему плагинов UI;
- реализовывать визуализацию графа как обязательное условие первого релиза;
- добавлять SSO/внешний identity provider;
- реализовывать встроенный PDF-вьюер с подсветкой координат;
- поддерживать несколько корпусов и переключение между ними;
- реализовывать сравнение содержания разделов до появления backend-контракта;
- реализовывать категории split/merge разделов, которых нет в анализаторе;
- реализовывать раздел Evaluation / Benchmark в рамках этой задачи: он выделен
  в `evaluation-webui.md` и использует отдельный API/storage.

Эти изменения могут рассматриваться отдельно, если появится обоснованная потребность.

## 17. Принцип реализации

Реализовывать постепенно, не заменяя работающую систему целиком.

Главный принцип:

**Новый UI должен улучшать представление результатов и взаимодействие с агентом,
но не становиться ещё одной реализацией самого агента.**

Существующий Python Agent_RAG остаётся центром выполнения исследований.
React становится полноценным клиентом для работы с ним.

Первый релиз включает только базовый чат, историю, реальные этапы и streaming
(в доступном объёме). Evidence, аналитические представления и сравнение структуры
добавляются последовательно, без блокирования первого работающего интерфейса.

### A.3. Покрытие

| Код | UI | Значение |
|---|---|---|
| `covered` | Найдено | есть подтверждающее evidence |

| `change_type` | UI | Не путать с |

| `renamed` | Переименован | изменение содержания |
| `restructured` | Перемещён / изменён уровень | разделение/объединение |
| `expanded` | Объём вырос | рост показателя |
| `reduced` | Объём сократился | падение показателя |
